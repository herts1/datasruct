## 一、哈希表基础

### Q1：为什么要选择哈希表作为存储结构？与顺序表、链表、二叉排序树相比有什么优势？

**答**：哈希表的查找时间复杂度为O(1)（均摊），而顺序表/链表的查找为O(n)，二叉排序树的查找为O(log n)。本题目需要频繁根据手机号码和姓名快速查找用户，哈希表是最优选择。具体对比：

| 结构 | 查找 | 插入 | 适用场景 |
|------|------|------|---------|
| 顺序表 | O(n) | O(1)/O(n) | 数据量小，不频繁查找 |
| 链表 | O(n) | O(1) | 频繁增删 |
| 二叉排序树 | O(log n) | O(log n) | 需要有序遍历 |
| **哈希表** | **O(1)** | **O(1)** | **频繁等值查找** |

### Q2：什么是哈希冲突？如何处理？

**答**：哈希冲突是指不同的关键字经过哈希函数计算后得到相同的地址。本系统实现了两种处理方法：

- **开放寻址法（线性探测）**：当发生冲突时，依次探测下一个位置 `(h+1)%size, (h+2)%size, ...` 直到找到空位。优点：实现简单，数组连续存储，缓存友好。缺点：可能产生"一次聚集"现象，装填因子较大时性能急剧下降。

- **链地址法（拉链法）**：每个哈希桶维护一个链表，冲突的元素追加到链表中（头插法）。优点：装填因子可大于1，删除方便，无聚集问题。缺点：需要额外指针空间，内存不连续导致缓存不友好。

### Q3：装填因子α是什么？它对性能有什么影响？

**答**：装填因子 α = 已插入记录数 / 哈希表大小。本系统中α = 30/61 ≈ 0.49。

- **线性探测成功查找ASL**：`(1 + 1/(1-α)) / 2`，当α=0.49时≈1.48；当α→1时，ASL急剧增大。
- **链地址法成功查找ASL**：`1 + α/2`，当α=0.49时≈1.25；随α线性增长。

结论：α<0.5时两者差距不大；α>0.75时线性探测性能急剧恶化，而链地址法保持平稳。因此开放寻址法适合α<0.75的场景，链地址法适用范围更广。

### Q4：线性探测中"墓碑"标记（valid=2）的作用是什么？为什么不能简单置为0？

**答**：在开放寻址法的删除操作中，不能简单将被删除位置置为空（valid=0），否则会破坏查找链的连续性。

例如：关键字A、B、C哈希值均为h，按线性探测依次存入h、h+1、h+2。如果删除B后将h+1置为空，后续查找C时会在h+1处遇到空位而错误返回"未找到"。因此引入valid=2（已删除）作为"墓碑"标记——查找时遇到valid=2继续探测，插入时遇到valid=2可复用该位置。

## 二、哈希函数设计

### Q5：你实现了哪两种哈希函数？各自的设计思路是什么？

**答**：

**除留余数法** `h(key) = key mod m`：
- 手机号：将11位数字转为`unsigned long`整数，对表长61取模。如 `13800138001 % 61`。
- 姓名：采用多项式哈希 `v = v * 31 + c`，乘数31是素数能减少聚集，且编译器可优化为 `(v << 5) - v` 提高效率。此方法被Java的`String.hashCode()`广泛使用。
- 表长61选为质数，能减少因模数存在因子导致的周期性聚集。

**折叠法**：
- 手机号：将11位号码拆分为前3位（网络识别号）、中4位（地区编码）、后4位（用户号码）三段，分别转为整数后求和取模：`(138 + 13 + 8001) % 61`。
- 姓名：每4个字符为一组，拼接为整数后累加取模。

### Q6：除留余数法为什么用31作为乘数？能不能用其他数字？

**答**：31具有以下优点：
1. **是素数**：素乘数能减少哈希值的周期性和聚集
2. **计算优化**：`v * 31 = (v << 5) - v`，一次移位+一次减法替代乘法，计算效率高
3. **经验验证**：Java的`String.hashCode()`使用31，经过数十年的广泛验证

可以用其他素数如33、37、131等，但31在均匀性和计算效率之间取得了最佳平衡。如果用偶数（如32），会丢失一位信息导致低位恒为零。

### Q7：为什么哈希表大小要取质数？你的表长61是如何确定的？

**答**：取质数的原因是减少除留余数法的聚集效应。如果表长m有因子d，那么哈希值相差d的倍数的关键字会聚集在一起。例如m=60=2×2×3×5，则所有哈希值相差2、3、5的关键字都可能冲突。

61是大于30（预期数据量）的最小质数，使装填因子α接近0.5（30/61≈0.49），在性能和空间之间取得平衡。

## 三、算法实现

### Q8：`count_calls()`函数的复杂度是多少？如何优化？

**答**：当前实现使用双重循环，时间复杂度O(N×M)，N=顾客数(30)，M=通话记录数(46)。

```c
for (int k = 0; k < call_cnt; k++)      // M次
    for (int i = 0; i < cust_cnt; i++)  // N次
        if (strcmp(..., call_from[k]) == 0) ...  // 字符串比较
```

**优化方案**：先用哈希表建立"手机号→顾客下标"的映射（O(N)），再单次遍历通话记录累加（O(M)），总复杂度降至O(N+M)。但这需要手机号到哈希表的完整映射，程序已具备该能力（phone_ch哈希表），可直接复用。

### Q9：链地址法为什么选择头插法而不是尾插法？

**答**：头插法（新节点插入链表头部）：
- 时间复杂度O(1)，只需修改table[h]指针
- 尾插法需要遍历整个链表找尾部，最坏O(n)
- 查找效率与插入顺序无关（都需要遍历链表比较关键字）

因此头插法在保证查找效率不变的前提下，插入效率更高。

### Q10：开放寻址法的查找终止条件是什么？

**答**：查找时顺序探测，遇到以下情况之一终止：
1. `valid == 0`（从未被占用的空位）→ 查找失败（返回-1）。因为如果有该关键字，插入时不会跳过空位。
2. `valid == 1` 且关键字匹配 → 查找成功，返回顾客下标。
3. `valid == 2`（已删除的"墓碑"）→ 继续探测，不终止。
4. 遍历了整个表且未找到 → 查找失败（返回-1），此时表满且关键字不存在。

## 四、程序设计与调试

### Q11：为什么要同时维护开放寻址和链地址两套哈希表？程序运行时用的是哪一套？

**答**：程序初始化时使用**链地址法**（`ch_init` + `ch_insert_*`）构建哈希表，供功能2（按姓名查找）和功能3（按手机号查找）使用。

功能4（哈希函数比较）和功能5（冲突处理方法比较）需要统计信息，通过`build_*`系列函数在临时表上重建，收集冲突次数和探测次数后输出对比结果。四套哈希表并行维护的设计，使得比较功能可以在不破坏主哈希表的前提下独立运行。

### Q12：你是如何测试程序正确性的？预期"聊天狂人"是谁？

**答**：

- **功能测试**：逐项测试菜单所有选项，验证输出正确性
- **数据验证**：手动统计通话记录，确认ZhangWei（13800138001）的通话次数为12次（主叫7次+被叫5次）
- **边界测试**：空输入、非法菜单输入、不存在的姓名/手机号
- **对比测试**：将程序输出的冲突率和ASL与理论公式计算值对比
- **大数据测试**：用50条扩展数据验证程序在大数据量下的稳定性

预期"聊天狂人"：**ZhangWei/张伟**，手机号**13800138001**，通话**12次**。

### Q13：你的程序中哪些函数声明为static？为什么？

**答**：哈希函数（`hash_div_phone`、`hash_fold_phone`、`hash_div_name`、`hash_fold_name`）和统一接口函数（`hash_phone`、`hash_name`）声明为static，限定其仅在`phone.c`内可见。

这样做的原因：
1. **封装性**：外部只需调用`oa_insert_*`或`ch_insert_*`等高级接口，无需知道内部哈希算法
2. **可维护性**：如需更换哈希函数，只影响`phone.c`内部，头文件和调用方无需修改
3. **符合工程规范**：模块内部实现细节不应暴露给外部

## 五、拓展与思考

### Q14：如果数据量扩大到10万条，当前设计存在哪些问题？如何改进？

**答**：存在以下问题及改进方案：

| 问题 | 改进方案 |
|------|---------|
| 哈希表大小固定61 | 实现动态扩容：当α>0.75时，表长扩至下一个质数（如131、257），重新哈希所有元素 |
| `count_calls()` 双重循环O(N×M) | 利用现有哈希表建立手机号映射，单次遍历O(N+M) |
| `MAX_CUSTOMERS=100`太小 | 改用动态数组或链表存储；或将哈希表值改为直接存储Customer而非下标 |
| 内存中存储所有通话记录 | 通话记录可流式读取，不全部加载到内存 |
| 字符串比较效率低 | 可将手机号存储为`unsigned long`（64位足以存11位数字），整数比较比`strcmp`快得多 |

### Q15：如果要支持模糊查找（如输入"张"找到所有姓张的用户），现有哈希表能实现吗？

**答**：不能。哈希表只能支持**精确等值查找**（给定完整关键字，返回唯一值）。模糊查找需要：
1. 遍历所有数据（O(n)），用`strstr`或正则匹配
2. 使用Trie树（前缀匹配）
3. 使用倒排索引（全文检索）

但对于题目要求的精确查找场景，哈希表是最优解。

### Q16：除留余数法和折叠法在你的数据上哪个冲突更少？为什么？

**答**：在本系统30条测试数据上，除留余数法的冲突率低于折叠法。

原因分析：
- 手机号除留余数法：将号码视为完整整数取模，分布均匀性取决于模数是否为质数（61是质数）
- 手机号折叠法：将号码分段相加，破坏了原始数字的结构特征——例如13800138001和13800138002折叠后仅差1（8001+13+138 vs 8002+13+138），但13900139001折叠后差很多（9001+13+139 vs 8002+13+138），不同号段间的折叠和可能意外碰撞

因此在本数据集上除留余数法表现更好，但折叠法在其他数据集（如号码不连续的随机数据）上可能更优。这也验证了"没有绝对最优的哈希函数，只有最适合特定数据分布的哈希函数"。
